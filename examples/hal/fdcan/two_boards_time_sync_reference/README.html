Example: hal_fdcan_two_boards_time_sync_reference

Example version: 2.0.0

How to distribute a time reference from a controller board to a responder board with FDCAN end-of-frame timestamping and HAL APIs.

1. Detailed scenario

Initialization phase: At main program start, the mx_system_init() function is called. It initializes the peripherals, nonvolatile memory, the system clock, and the SysTick.

The application executes the following example steps:

Step 1: initializes the FDCAN instance and the generated timer capture path. registers the callbacks used during the synchronization cycle.

Step 2: starts the transmit end-of-frame timestamp capture to get local time.

Step 3: reads the current controller local time. sends a SYNC frame carrying the whole-seconds part of this time. waits for SYNC transmission and validates the transmit timestamp capture.

Step 4: stops the timestamp capture window. sends a follow_up frame carrying the nanoseconds remainder in the current second. resets the synchronization state, then starts a new synchronization cycle.

End of example: The controller keeps sending SYNC and follow_up frames indefinitely every second if no error occurs.

Sequence diagram

The sequence diagram shows how the controller sends a SYNC frame and then a FOLLOW_UP frame to distribute a precise time reference. On the responder side, the TIM -> DMA -> CPU callback chain processes the Follow Up reception to reconstruct the full timestamp.

If you enable USE_TRACE, you can follow the synchronization cycles, in the nominal case of execution, in the terminal logs:


[INFO] Reference: initialization COMPLETED. Starting time synchronization.
[INFO] Reference: SYNC sent (seconds = 12), FOLLOW_UP sent (nanoseconds = 345678000). Reference time = 12345678000 ns.
[INFO] Reference: SYNC sent (seconds = 13), FOLLOW_UP sent (nanoseconds = 346789000). Reference time = 13346789000 ns.

2. Example configuration

This example demonstrates the FDCAN peripheral configured as indicated below:

  • The FDCAN standard (11 bits) frame format is selected.
  • The FDCAN IP is configured to run at 500 kbit/s for nominal phase (sampling point at 75%) and 2 Mbit/s for data phase (sampling point at 80%).
  • The FDCAN-bus timings are directly generated by STM32CubeMX2 by referring to the FDCAN initialization section in the reference manual.
  • The selected GPIO pins support the FDCAN alternate function. They are configured in push pull mode.
  • The frames use FDCAN FD format with bit-rate switching and an 8-byte payload.
  • The generated timer runs with a 125 ns time base.
  • One timer capture channel is connected internally to FDCAN1_TX to timestamp the end of transmission.
  • The FDCAN Tx mode is configured in FIFO mode. It can optionally be configured in Queue mode: Messages stored in the Tx queue will be transmitted starting with the message with the lowest message ID (highest priority) instead of First In First Out.

3. Hardware environment and setup

3.1. Generic Setup

The FDCAN bus uses CAN_H and CAN_L lines and requires a CAN or FDCAN transceiver.

No extra external wire is required between FDCAN and TIM because the end-of-frame event is routed internally inside the MCU.

3.2. Specific board setups

The example is developed only for NUCLEO-C542RCand NUCLEO-C562RE. NUCLEO-C5A3ZG is not supported because it has no onboard FDCAN transceiver.

4. Troubleshooting

Here are the points of attention for this specific example:

  • Start the responder example before starting the controller example.
  • Keep the same nominal and data bit timings on both boards.
  • The responder filter must accept the standard identifier 0x111 before the FDCAN peripheral is started.
