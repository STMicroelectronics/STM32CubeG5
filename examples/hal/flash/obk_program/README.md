# __Example: *hal_flash_obk_program*__

**Example version:** 2.0.0

[![User Manual](doc/read_the-UM.svg)](https://dev.st.com/stm32cube-docs/examples/arch-v1/en/index.html "An offline version is also available in the Cube firmware package.")

How to use the FLASH interface to perform programming operations on option-byte key (OBKeys) areas and verify read access for each area at different hide-protect levels (HDPL).
All operations are executed from the **secure** context in **polling mode**.


## __1. Detailed scenario__

__Initialization phase__: At the beginning of the main program, the `mx_system_init()` function is called to initialize the peripherals, the FLASH interface, the system clock, and the SysTick.

The application executes the following __example steps__:

__Step 1__: Initialize the FLASH instance and prepare OBKeys access (retrieve the FLASH handle from the generated code, unlock the FLASH interface control, and select the OBK-HDPL so that OBK1 is accessible from the current HDPL).

__Step 2__: Read the current HDPL level and print its encoded value and a symbolic name.

__Step 3__: Program **OBKeys area 1** with a data pattern (two 128-bit quadwords) using the recommended erase / program / swap sequence.

__Step 4__: Increase the OBK-HDPL and program **OBKeys area 2** with the same data pattern, again using the erase / program / swap sequence.

__Step 5__: Increase the OBK-HDPL once more and program **OBKeys area 3** with the data pattern using the same sequence.

__Step 6__: Increase the global HDPL level step by step until it reaches HDPL3.

__Step 7__: Read back from each provisioned OBKeys area to verify the expected isolation behavior:

- **OBKeys area 1** and **OBKeys area 2** must be hidden (Read-As-Zero plus OBKeys access error).
- **OBKeys area 3** must remain readable (reference data pattern visible with no OBKeys error).

__Step 8__: Lock the FLASH interface control again, deinitialize the FLASH instance, and print a final message confirming that the FLASH interface is locked.

__End of example__: After __Step 8__, the example is completed.

The OBKeys area registers are configured on-the-fly and automatically return to their default state after a system reset.

The example status is reported via the variable **`ExecStatus`**, and the status LED remains turned on in case of success.

You can also check the contents of the memory after programming it.

If you enable `USE_TRACE`, you can follow these execution steps in the terminal logs:

```text
[INFO]  Step 1: Device initialization completed - FLASH interface is UNLOCKED.
[INFO]  Step 2: Initial HDPL level is HDPL1 (encoded value 0x51).
[INFO]  Step 3: Provision OBKey area 1 using erase / program / swap sequence.
[INFO]  Step 4: Increment OBK-HDPL and provision OBKey area 2.
[INFO]  Step 5: Increment OBK-HDPL and provision OBKey area 3S.
[INFO]  Step 6: HDPL is now set to HDPL3 (encoded value 0x6F).
[INFO]  Step 7: OBKeys readings at HDPL3 match the expected HDPL isolation pattern.
[INFO]  Step 8: Device de-init COMPLETED - FLASH interface is LOCKED.
...
```


## __2. Example configuration__

[![Configuration Manual](doc/configure_with-ConfigurationMa.svg)](https://dev.st.com/stm32cube-docs/examples/arch-v1/en/configure/config_toc.html "An offline version is also available in the STM32Cube firmware package.")

This example uses the default project configuration generated by STM32Cube for the selected device:

- FLASH interface enabled with OBKeys support.
- Security subsystem enabled to provide HDPL and OBK-HDPL selection.
- Debug / trace interface enabled to display run-time messages.
- All operations executed from the non-secure context in polling mode.

No additional user configuration is required for the basic scenario described here.
Refer to the project configuration files if you need to adapt clocking, security, or debug settings to your environment.


## __3. Hardware environment and setup__

### __3.1. Generic Setup__

Before running the example:

- Use an STM32 board that provides an FLASH interface with OBKeys and HDPL support.
- Power the board and connect it to the host PC through the on-board debug interface.
- Program the example binary by using an appropriate tool (for example STM32CubeProgrammer or the IDE integration).
- Open a serial terminal on the board's virtual COM port (for example at 115200 baud, 8-N-1) to monitor the example logs.

## __4. Troubleshooting__

[![Troubleshooting](doc/debug_with-Troubleshooting.svg)](https://dev.st.com/stm32cube-docs/examples/arch-v1/en/debug/debug_toc.html "An offline version is also available in the STM32Cube firmware package.")

- **No messages on the terminal**
  - Check the board power supply and USB / ST-LINK connection.
  - Verify that the serial terminal is configured on the correct COM port and baud rate.

- **OBKeys programming errors reported in the logs**
  - Ensure that the device option bytes are in a configuration compatible with this example.
  - Perform a full chip erase with your programming tool, then rebuild and re-flash the example.

- **HDPL / OBKeys readback checks report an error**
  - Make sure no other application code is modifying HDPL or OBKeys configuration.
  - Reset the device and re-run the example so that the complete sequence (initialization, OBKeys provisioning, HDPL increase, and readback) is executed from a clean state.
  - If the HDPL3 checks still report an error, compare the observed behavior with the HDPL / OBKeys rules described in the device reference manual for your series.
