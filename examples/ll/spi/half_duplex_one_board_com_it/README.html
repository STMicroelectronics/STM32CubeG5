Example: ll_spi_half_duplex_one_board_com_it

Example version: 2.0.0

How to manage a half-duplex SPI communication on one single board, using the LL API.

1. Detailed scenario

This example uses 2 SPI instances on the same board, one in controller mode and the other in responder mode.

Initialization phase: At main program start, the mx_system_init() function is called. It initializes the peripherals, nonvolatile memory (such as flash memory, NVM, or external memories), MPU regions (if applicable), the system clock, and the SysTick.

The application executes the following example steps:

Step 1: configures and initializes the two SPI instances in IT mode.

Step 2: the SPI responder side prepares the communication in half-duplex receive mode, using interrupts, waiting for the SPI controller to initiate the communication.

Step 3: The SPI controller side initiates the communication in half-duplex transmit mode, using interrupts, by sending data to the SPI responder over the single bidirectional data line. The SPI messages exchanged are null-terminated strings.

Step 4: Waits for the transfer complete interruption for both SPI instances, or a transfer error interruption on one of them.

Step 5: The SPI controller side prepares the communication in half-duplex receive mode, using interrupts, waiting for the SPI responder to initiate the communication.

Step 6: The SPI responder side initiates the communication in half-duplex transmit mode, using interrupts, by sending data to the SPI controller over the single bidirectional data line. The SPI messages exchanged are null-terminated strings.

Step 7: Waits for the transfer complete interruption for both SPI instances, or a transfer error interruption on one of them.

Step 8: Checks that the sent and received buffers match.

On most boards, the LED shares its pin with the SPI SCK. Therefore, this example does not have a status LED.

End of example: While no error occurs, the data is transferred 10 times between the controller and the responder. In case of failure or the maximum number of attempts is reached, the data transfer is stopped and an error status is reported to the main() function.

If the data transmit or receive operation fails or the exchanged buffers are different, the controller restarts the communication by sending again the same message. The error_handler() function is called when the maximum number of attempts is reached.

2. Example configuration

The example demonstrates the following peripheral:

SPI:

The example uses SPI half-duplex synchronous transfers on two lines (MOSI for the controller and MISO for the responder, plus the clock signal). The controller transmits and the responder receives over the single shared data line, in interrupt mode.

  • SPI controller: One first instance is configured as controller, it handles the clock for the transmission
  • SPI responder: One second instance is configured as responder

In addition, it is necessary to set the clock polarity as either LOW or HIGH. Also configure the clock phase to:

  • Either one edge if the first clock transition corresponds to the first data capture edge,
  • Or two edges if the second clock transition represents the first data capture edge.

For the current project, the clock polarity is set to LOW, while the clock phase is configured as one edge.

4. Troubleshooting

Find below the points of attention for this specific example.

GPIO speed: The GPIO slew rate is an important parameter that affects the performance of high-frequency signals. Refer to application note AN4899 in case of issues. AN4899

LED twinkling: Most boards have a LED connected to the same pin as SPI SCK from arduino connector. This LED can twinkle during SPI communications.

Error handling: In LL examples, error handling is controlled by the USE_LL_APP_ERROR constant in the application files to reduce code footprint. This compilation flag is disabled by default. If the example does not behave as expected, enable error handling for debugging by setting USE_LL_APP_ERROR to 1 in ll_example.h.
